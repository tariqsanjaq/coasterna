# Navigation fix — stray back arrow on Home after student sign-in

Date: 2026-09-01

## Bug report (from manual testing / video evidence)

After a student signs in successfully, the resulting Home screen shows a back
arrow in its AppBar. Tapping back returns to the Sign In screen post-login,
and further back-presses can reach a stale screen or exit unexpectedly.

## Step 1 — investigation (read fresh, files as they stood before any edit)

### Navigation topology (confirmed via grep across `lib/`)

- `lib/main.dart:29` — mobile home route is `SplashScreen`; web home route
  (`kIsWeb`) is `AdminLoginScreen`.
- `lib/features/splash/presentation/splash_screen.dart:24-28` — after a
  1000ms timer, `pushReplacement`s the root `SplashScreen` with `HomePage`
  (guest). This is correct: replacing the app's own root route leaves a
  1-deep stack, no back arrow.
- `lib/features/search/presentation/home_page.dart:296-301` — the AppBar
  "Sign in" `IconButton` (shown only when `_authRepository.currentUser ==
  null`) calls `Navigator.push(context, MaterialPageRoute(builder: (_) =>
  const StudentLoginScreen()))`. This is a genuine `push`, so the stack
  becomes `[HomePage(guest), StudentLoginScreen]`.
- `student_login_screen.dart` — "Create an account" `TextButton` (line
  150-155, unchanged) does `Navigator.of(context).push(MaterialPageRoute(...
  StudentSignUpScreen()))`, another genuine push. Stack becomes
  `[HomePage(guest), StudentLoginScreen, StudentSignUpScreen]`.
- `StudentLoginScreen` is pushed from exactly one call site
  (`home_page.dart:299`); `grep` confirms no other file references it.
  `AdminLoginScreen` is referenced only as `main.dart`'s `home:` (the app
  root on web) and as the `pushAndRemoveUntil` target of
  `admin_home_screen.dart`'s sign-out flow — it is never itself `push`ed on
  top of another screen.

### Exact Navigator call on successful sign-in (student)

`lib/features/auth/presentation/student_login_screen.dart:63-67` (before fix):

```dart
void _goToHome() {
  Navigator.of(context).pushReplacement(
    MaterialPageRoute(builder: (context) => const HomePage()),
  );
}
```

Called from `_signIn()` at line 53 on success, and from the "Continue
without signing in" `OutlinedButton` at line 160 (`onPressed: _isLoading ?
null : _goToHome`) — both paths share this one method.

`pushReplacement` only swaps out the **top** route. Since `StudentLoginScreen`
sits on top of `HomePage(guest)`, the result is
`[HomePage(guest, stale), HomePage(signed-in)]` — a 2-deep stack, hence the
back arrow. Tapping back lands on the stale guest `HomePage` instance
(built before sign-in, so it doesn't reflect the new auth state), and a
second back-press exits the app (since the guest `HomePage` is the actual
root pushed by `SplashScreen`).

### Exact Navigator call on successful sign-up

`lib/features/auth/presentation/student_signup_screen.dart:57-63` (before
fix):

```dart
try {
  await _authRepository.signUp(email: email, password: password);
  if (!mounted) return;
  Navigator.of(context).pushReplacement(
    MaterialPageRoute(builder: (context) => const HomePage()),
  );
}
```

Same defect, and it is reached one level deeper: `StudentSignUpScreen` sits
on top of `[HomePage(guest), StudentLoginScreen]`, so `pushReplacement`
leaves `[HomePage(guest, stale), StudentLoginScreen, HomePage(signed-in)]` —
this is the exact scenario the bug report describes: back arrow shows, and
tapping back returns to the **Sign In screen** post-signup. A second
back-press then reaches the stale guest Home, and a third exits the app.

### Admin login screen — same pattern, but not buggy

`lib/features/admin/presentation/admin_login_screen.dart:69-72` (unchanged,
not touched by this fix):

```dart
Navigator.of(context).pushReplacement(
  MaterialPageRoute(builder: (context) => const AdminHomeScreen()),
);
```

This uses the identical `pushReplacement` pattern, but it is **not** buggy:
`AdminLoginScreen` is only ever reached as `main.dart`'s `home:` route on
web (`kIsWeb ? const AdminLoginScreen() : const SplashScreen()` —
`main.dart:29`), i.e. it *is* the navigator root. There is nothing beneath
it to leave stranded, so `pushReplacement` here already produces a 1-deep
stack with no back arrow. Confirmed via grep that no other file pushes
`AdminLoginScreen` on top of another screen. Left as-is — no fix needed.

Admin sign-out (`admin_home_screen.dart:112-115`) already uses
`pushAndRemoveUntil` back to `AdminLoginScreen`, so that direction was
already correct.

### "Continue without signing in" (guest) path

Investigated per instructions. The guest button
(`student_login_screen.dart:159-162`) calls the exact same `_goToHome()`
method used by the post-sign-in success path — there is only one call site
for this navigation logic, not two separate ones. It therefore has the
identical `pushReplacement`-without-clearing bug (stack becomes
`[HomePage(guest, stale), HomePage(guest, new)]`, back arrow, back-press
lands on a stale guest Home). Because it is the *same* method, not a
separate implementation, fixing `_goToHome()` fixes both the sign-in
success path and the guest path together — there was no way to fix one
without the other, and no separate guest-only fix was written.

## Step 2 — fix applied

Both spots that push towards a signed-in/guest `HomePage` after auth now
clear the entire back stack:

**`lib/features/auth/presentation/student_login_screen.dart`** —
`_goToHome()`:

```dart
void _goToHome() {
  Navigator.of(context).pushAndRemoveUntil(
    MaterialPageRoute(builder: (context) => const HomePage()),
    (route) => false,
  );
}
```

**`lib/features/auth/presentation/student_signup_screen.dart`** — signup
success branch:

```dart
await _authRepository.signUp(email: email, password: password);
if (!mounted) return;
Navigator.of(context).pushAndRemoveUntil(
  MaterialPageRoute(builder: (context) => const HomePage()),
  (route) => false,
);
```

`(route) => false` rejects every predicate check, so every existing route —
`HomePage(guest)`, `StudentLoginScreen`, and (for signup) `StudentSignUpScreen`
— is discarded regardless of how many screens were pushed to get there. The
resulting `HomePage` has an empty back stack, matching the pattern already
used correctly by both sign-out flows.

`AdminLoginScreen`'s `pushReplacement` on line 70 was **not** changed — see
above, no back-stack bug exists there.
